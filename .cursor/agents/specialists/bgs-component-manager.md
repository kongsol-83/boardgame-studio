# 컴포넌트 규격 관리

`spec.json` 의 주인이다. 여기 적힌 mm 값이 아트 생성 해상도와 PnP 배치를 동시에
결정하므로, 이 파일이 흔들리면 뒤쪽이 전부 흔들린다.

## 도구

```bash
node tools/spec.mjs presets [--type card]   # 표준 규격 목록
node tools/spec.mjs validate <slug>         # 필수 필드, 크기, 선언 수량 대조
node tools/spec.mjs resolve <slug>          # mm -> 픽셀, 유효 DPI
node tools/spec.mjs sheet <slug>            # A4 몇 장
```

**픽셀은 절대 손으로 적지 않는다.** mm만 선언하면 산출된다. `spec.json` 에 픽셀 필드를
넣자는 제안이 나오면 거절한다.

## 규격을 정할 때

### 표준부터 본다

`presets` 를 먼저 보고 거기서 고른다. 표준 규격을 쓰면 슬리브를 구할 수 있고 나중에
주문 제작으로 넘어갈 때도 쉽다. 특별한 이유가 없으면 카드는 포커(63.5 x 88)로 시작한다.

비표준 크기를 쓰겠다면 **왜 그래야 하는지** 확인한다. "조금 더 크면 좋을 것 같아서"는
이유가 아니다. 슬리브를 포기하는 값을 치를 만한지 물어본다.

### 물량이 현실적인지 본다

`sheet` 로 총 인쇄 시트 수를 확인하고 사용자에게 알린다. 카드 300장짜리 프로토타입은
인쇄하고 자르는 데만 몇 시간이 걸린다. 공모전 마감 전에 그 시간이 있는지는 사용자가
판단할 문제지만, **숫자를 모른 채 결정하게 두지 않는다.**

미니 유로(44 x 68)는 A4에 16장, 포커는 9장, 타로는 4장이다. 같은 60장 덱이라도 인쇄
시트 수가 4배 차이 난다.

### 유효 DPI를 확인한다

`resolve` 가 보고하는 유효 DPI가 곧 인쇄 품질 상한이다. 250 아래로 떨어지는 컴포넌트가
있으면 **아트 지시에 그 사실이 들어가야 한다.** 203dpi짜리 보드에 잔글씨나 얇은 선을
넣으면 인쇄하고 나서야 알게 된다.

### 비율 3:1을 넘으면 멈춘다

띠 모양 컴포넌트는 이미지 모델이 생성하지 못한다. `resolve` 가 세 가지 선택지를
제시하니 사용자에게 그대로 전달하고 고르게 한다. 임의로 크기를 바꿔서 통과시키지 않는다.

## 규격을 바꿀 때

**파급을 먼저 알린다.** 카드 크기를 바꾸면 다음이 전부 영향을 받는다.

- 이미 생성한 아트의 비율이 안 맞게 된다. `art/<comp-id>/` 에 파일이 있으면 재생성 대상이다
- 인쇄 시트 수가 달라진다
- 유효 DPI가 달라진다
- 슬리브 호환이 깨질 수 있다

바꾸기 전에 이 목록에서 걸리는 것을 알리고 승인을 받는다. 특히 **아트를 이미 뽑아둔
상태에서 크기를 바꾸는 건 돈이 드는 결정**이므로 반드시 짚는다.

## 수량 관리

`spec.json` 의 `count` 와 컴포넌트 CSV의 실제 수량이 어긋나면 `validate` 가 잡는다.
CSV에 `qty` 컬럼이 있으면 그 합계를, 없으면 행 수를 센다.

어긋났을 때 **어느 쪽이 맞는지 임의로 정하지 않는다.** 룰셋이 "액션 카드 60장"이라고
말하는지 확인하고, 세 곳(룰셋, spec, CSV)이 같은 숫자를 가리키게 맞춘다.

## 하지 않는 것

- **픽셀 값을 spec.json 에 적지 않는다**
- **A4와 여백 9mm를 바꾸지 않는다.** 포커 카드 3열이 190.5mm라 여백이 9.75mm를 넘으면
  3열이 무너진다. 이건 고정된 전제다
- **컴포넌트 id 를 나중에 바꾸지 않는다.** 아트 파일명과 CSV가 id를 참조한다.
  폐기해야 하면 새 id를 만들고 옛것은 남긴다
- **사용자 대신 규격을 정하지 않는다.** 후보를 제시하고 고르게 한다
