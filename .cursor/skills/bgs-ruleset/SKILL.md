# 룰셋 작성

`projects/<slug>/ruleset.md` 하나를 쓴다. **설계 사양과 룰북을 분리하지 않는다.**

두 문서를 따로 두면 반드시 어긋난다. 처음부터 플레이어가 읽을 수 있는 형태로 쓰고,
설계 메모는 `concept.md` 에 남긴다.

문서 언어는 `studio.config.json` 의 `language` 를 따른다.

## 두 가지 규칙

이 스킬의 핵심이다. 나머지 절차는 이 둘을 지키려고 있다.

**모든 수치는 본문이 아니라 표에 모은다.** 본문에는 "라운드 시작에 카드를 보충한다"라고
쓰고 몇 장인지는 표에서 참조한다. 밸런싱은 수치를 계속 바꾸는 일인데, 숫자가 본문에
흩어져 있으면 개정할 때마다 문서 전체를 뒤져야 하고 반드시 하나를 빠뜨린다.

**인원에 따라 달라지는 값만 인원별 열로 나눈다.** 셋업 자원, 라운드 수, 시장 공개 장수처럼
인원이 늘면 조정하게 되는 값들이다. 반대로 인원과 무관한 값에 2인/3인/4인 열을 만들고 같은
숫자를 세 번 적으면 표가 거짓말을 한다. 읽는 사람은 열이 나뉘어 있으면 인원별로 다를 것이라
기대하고, 그게 아니라는 걸 알아채는 데 시간을 쓴다. **표를 둘로 나눈다.**

## 진행

```
- [ ] 1. 무엇을 쓸지 확인한다 (신규 / 개정)
- [ ] 2. 구조를 잡는다
- [ ] 3. 본문을 쓴다
- [ ] 4. 수치를 표로 뽑는다
- [ ] 5. 예외 상황을 채운다
- [ ] 6. 버전과 변경 이력을 남긴다
```

### 1. 신규인가 개정인가

**개정이면 무엇을 왜 바꾸는지 먼저 확인한다.** 검토 리포트나 플레이테스트 기록이 근거로
있어야 한다. 근거 없이 "더 나을 것 같아서" 고치면 다음 판에서 무엇이 효과가 있었는지
알 수 없게 된다.

**한 번에 여러 곳을 고치지 않는다.** 검토에서 지적이 다섯 개 나왔어도 치명 항목만
반영하고 나머지는 남긴다. 이건 게으름이 아니라 인과를 지키는 문제다.

**막히면 `bgs-design-lead` 를 부른다.** 무엇부터 손댈지 모르겠거나 검토 결과가 여럿이라
우선순위가 안 잡힐 때다. 리드가 필요한 스페셜리스트를 골라 병렬로 돌리고 결과를 합쳐준다.

각도가 이미 분명하면 스페셜리스트를 직접 불러도 된다.

| 지금 필요한 것 | 부를 사람 |
| --- | --- |
| 규칙 구조, 액션 집합, 코어 루프 | `bgs-system-designer` |
| 카드 종류와 덱 구성 | `bgs-content-designer` |
| 테마 붙이기, 이름, 용어 통일 | `bgs-narrative-designer` |
| 수치 확정 | `bgs-balance-designer` |

### 2. 구조

**승리 조건을 앞에 둔다.** 목표를 모르는 채로 액션 설명을 읽으면 아무것도 이해되지 않는다.
잘 만든 룰북은 예외 없이 "이 게임에서 이기려면 무엇을 해야 하는가"를 먼저 말한다.

```
1. 개요          한 문단. 무엇을 하는 게임이고 몇 명이 몇 분 하는가
2. 구성물        목록과 수량
3. 승리 조건     여기가 앞이다
4. 셋업
5. 라운드 진행   전체 흐름을 먼저, 그다음 각 페이즈
6. 액션 상세
7. 게임 종료와 점수 계산
8. 수치표        인원별로 달라지는 것과 아닌 것을 나눠서
9. 예외 상황
10. 용어
11. 변경 이력
```

### 3. 본문

- **한 문단에 한 규칙.** 두 규칙이 한 문단에 있으면 하나는 반드시 놓친다
- **예시를 붙인다.** 조금이라도 헷갈릴 규칙에는 구체적인 예를 하나 넣는다.
  "예: 파랑 3개와 빨강 1개가 있는 플레이어가..." 처럼
- **용어를 고정한다.** "자원"으로 부르기로 했으면 끝까지 자원이다. "재화"로 바꾸지 않는다
- **"할 수 있다"와 "해야 한다"를 구분한다.** 선택인지 강제인지가 안 드러나면 그 자리에서
  테이블마다 다르게 플레이하게 된다

### 4. 수치표

```markdown
## 수치

### 셋업
| 항목 | 2인 | 3인 | 4인 |
| --- | --- | --- | --- |
| 시작 자원 | 5 | 4 | 3 |
| 시작 손패 | 4 | 4 | 3 |
| 시장 공개 장수 | 4 | 5 | 6 |

### 진행
| 항목 | 2인 | 3인 | 4인 |
| --- | --- | --- | --- |
| 라운드 수 | 8 | 7 | 6 |
| 라운드당 액션 | 3 | 3 | 3 |

### 점수
| 항목 | 값 |
| --- | --- |
| 목표 달성 | 3점 |
| 남은 자원 2개당 | 1점 |
```

위에서 셋업과 진행은 인원마다 값이 다르므로 열을 나눴고, 점수는 인원과 무관하므로 `항목 | 값`
두 열이다. **인원별 열을 만들었는데 세 값이 전부 같다면 그 행은 아래 표로 내린다.**

컴포넌트 수량은 이 표에 넣지 않는다. `spec.json` 과 컴포넌트 CSV가 원본이고, 룰북의
구성물 절에서 참조한다. 두 곳에 적으면 반드시 어긋난다.

### 5. 예외 상황

**이 절을 비워두고 넘어가지 않는다.** 여기가 비면 `bgs-rules-critic` 이 반드시 잡는다.
미리 채우는 편이 왕복이 줄어든다.

최소한 이것들에 답한다.

- 덱이 떨어지면
- 자원이나 토큰이 동나면
- 동점이면 (최종 점수와 중간 경합 둘 다)
- 낼 수 있는 게 없으면
- 최대치를 넘기면
- 효과가 동시에 발생하면 순서가 무엇인가

### 6. 버전과 변경 이력

문서 상단에 버전과 날짜를 둔다.

```markdown
# <제목> 룰북

버전 0.4 · 2026-08-02
```

하단에 변경 이력을 남긴다. **한 줄에 세 조각을 쓴다.**

```markdown
## 변경 이력

### 0.4 — 2026-08-02
- 시작 자원을 5에서 4로 (3인) / 왜: 3인에서 초반 확장이 너무 빨라 4라운드에 게임이
  결정됨 / 확인: 3인 3판에서 승부가 6라운드 이후까지 가는가

### 0.3 — 2026-07-28
- ...
```

이유 없는 변경 이력은 나중에 되돌릴 때 아무 도움이 안 된다. **무엇을 확인하려고 바꿨는지**를
빼놓지 않는다. 그게 다음 플레이테스트에서 볼 것이 된다.

플레이테스트 기록에 "v0.4로 테스트"라고 적히므로, 나중에 밸런스가 좋아졌을 때 어느 변경
덕인지 추적된다. 버전이 없으면 이 연결이 통째로 끊긴다.

## 주의

**분량을 자랑하지 않는다.** 룰북이 길다는 건 대개 규칙이 많다는 뜻이고, 규칙이 많으면
배우는 시간이 길어진다. 공모전 심사에서 시연 시간은 실제 제약이다. 한 규칙을 넣을 때마다
"이게 없으면 게임이 안 되는가"를 묻는다.

**세계관을 룰북에 길게 쓰지 않는다.** 한 문단이면 충분하다. 테마는 설명이 아니라 룰과
컴포넌트로 전달되는 게 낫다.
